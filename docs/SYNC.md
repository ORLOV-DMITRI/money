# Синхронизация и общий бюджет (Supabase) — черновик дизайна

> Статус: **обсуждаем**. Открытые вопросы — в конце документа. Код не начат.

## Цель

Дима и жена ведут один семейный бюджет с двух (и более) телефонов. Ввод остаётся мгновенным и работает без сети, изменения одного видны другому за секунды.

## Принцип: local-first

```
 Телефон Димы                         Supabase                       Телефон жены
┌──────────────┐   push (outbox)   ┌──────────────┐   realtime    ┌──────────────┐
│ UI → Dexie   │ ────────────────▶ │  Postgres    │ ────────────▶ │ Dexie → UI   │
│ (мгновенно)  │ ◀──────────────── │  + RLS       │ ◀──────────── │              │
└──────────────┘   pull (since)    └──────────────┘    push       └──────────────┘
```

- Источник правды для UI — по-прежнему локальная Dexie: интерфейс и аналитика почти не меняются.
- Каждое изменение пишется локально и попадает в очередь отправки (outbox).
- Когда есть сеть: отправляем очередь, забираем чужие изменения «с момента последней синхронизации».
- Supabase Realtime сообщает «в семье что-то поменялось» → делаем pull.
- Балансы, отчёты и подсказки по-прежнему считаются на устройстве из полной истории.

## Модель: семья (household)

```
households          { id, name, created_at }
household_members   { household_id, user_id, role: owner|member, display_name, joined_at }
household_invites   { code, household_id, created_by, expires_at, used_by? }
```

- Все данные (`accounts`, `categories`, `transactions`, `purchase_items`, `products`, `stores`, `goals`, `budgets`, `recurring`, `templates`) получают `household_id`.
- **RLS**: строку видит и меняет только участник её семьи.
- Вступление в семью — по коду/ссылке приглашения через RPC `join_household(code)` (security definer), код одноразовый и живёт 48 часов.
- Тема и прочие настройки устройства остаются локальными.

### Кто потратил

Каждая операция хранит `created_by`. Это даёт:
- аватар/инициал в ленте («Ж» / «Д»);
- фильтр и отчёт «по людям»;
- подсказки вроде «Дима в этом месяце потратил на такси на 40% больше».

## Идентификаторы: UUID вместо автоинкремента

Автоинкрементные id двух телефонов неизбежно столкнутся. Переходим на **UUID v7** (сортируемые по времени), генерируемые на клиенте — запись создаётся офлайн без сервера.

### Детерминированные id там, где возможны дубли

| Ситуация | Риск | Решение |
| --- | --- | --- |
| Оба телефона офлайн создали продукт «Молоко» | два продукта-дубля | `id = uuidv5(household_id + "product:" + key)` — одинаковый на обоих устройствах, upsert склеит |
| То же с магазином «Magnum» | дубль | `uuidv5(household_id + "store:" + key)` |
| Регулярный платёж «Аренда» в режиме «авто» — оба телефона открыли приложение 7-го | **аренда запишется дважды** | `id = uuidv5(recurring_id + ":" + date)` — повторная запись станет тем же upsert |
| Стартовые категории создаются на каждом устройстве | дубли категорий | создаются один раз при создании семьи (на сервере, в RPC `create_household`) |

## Синхронизация

Служебные поля в каждой таблице (и в Postgres, и в Dexie):

| Поле | Где ставится | Зачем |
| --- | --- | --- |
| `updated_at` | **сервером** (триггер `now()`) | курсор pull; не зависит от часов на телефоне |
| `deleted_at` | клиентом | мягкое удаление — иначе удаление не «доедет» до второго телефона |
| `created_by` | клиентом, проверяется RLS | «кто потратил» |
| `_dirty` | только в Dexie | строка ждёт отправки |

**Push.** Пачками `upsert` всех `_dirty` строк, по порядку зависимостей (счета → категории → продукты/магазины → операции → позиции чека). После успеха снимаем `_dirty`.

**Pull.** `select * where household_id = ? and updated_at > last_pulled_at` по каждой таблице → `bulkPut` в Dexie (кроме строк, у которых локально `_dirty` — их сначала отправим).

**Конфликты.** Last-write-wins по строке: кто позже отправил — того версия. Для личных финансов это нормально: одну и ту же операцию вдвоём редактируют редко. Позже можно сделать слияние по полям.

**Чек** (операция + позиции) отправляется атомарно через RPC `upsert_receipt`, чтобы второй телефон не увидел операцию без позиций.

## Вход

Код из письма (email OTP, 6 цифр) — лучше «волшебной ссылки» для PWA: ссылка открывается в браузере, а не в установленном приложении, и сессия теряется. Google-вход можно добавить позже.

## Перенос текущих данных

При первом входе, если на устройстве есть данные: «Перенести данные с этого телефона в семью?» → перегенерируем id в UUID с сохранением связей → отправляем. Демо-данные переносить не предлагаем.

## Что меняется в коде

- `lib/db`: новая версия схемы Dexie (UUID-ключи, служебные поля, outbox), миграция с v1.
- `lib/services`: все записи идут через один слой, который ставит `_dirty`, `created_by`, мягко удаляет.
- `lib/sync`: push / pull / realtime / статус («синхронизировано», «нет сети», «3 изменения ждут отправки»).
- `supabase/migrations`: схема Postgres, RLS-политики, триггеры `updated_at`, RPC.
- UI: экран входа, «Семья» в настройках (участники, приглашение), инициалы в ленте, отчёт по людям, индикатор синхронизации.
- Тесты: синхронизация двух «устройств» на двух экземплярах Dexie против мок-сервера; RLS — тестами на SQL.

## Инфраструктура

- Проект Supabase создаёт Дима (нужны `SUPABASE_URL` и публичный `anon key`; ключ можно хранить во фронтенде — защищает RLS).
- Фронтенд остаётся статическим (Vercel/Netlify).
- Проверить актуальные лимиты бесплатного тарифа (в т. ч. «засыпание» неактивных проектов) перед запуском.
