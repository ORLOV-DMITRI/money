# Синхронизация через Supabase

> Статус: **реализовано 2026-11-03**. Проверено: схема и RLS — на локальном Postgres 16, движок — тестами двух «устройств», полный путь — в браузере против поддельного Supabase. Живую проверку на проекте делает Дима.

## Сценарий

Один общий аккаунт на семью. Чаще всего — с компьютера, иногда — с планшета.

| Вопрос | Решение |
| --- | --- |
| Личные счета/копилки | Нет — всё общее |
| Отчёт «кто потратил» | Не нужен |
| Вход | Email + пароль, один аккаунт на двоих, сессия запоминается |
| Перенос данных | Автоматически из старой локальной базы, если она есть |
| Бюджеты | Общие |
| Счета | Нет — «единые деньги» |

Без переменных окружения Supabase приложение работает как раньше: локально, без входа.

## Как устроено

```
 Компьютер                             Supabase                            Планшет
┌────────────────────┐  push (outbox) ┌────────────────┐    realtime     ┌────────────────────┐
│ UI → Dexie         │ ─────────────▶ │ Postgres + RLS │ ──────────────▶ │ Dexie → UI         │
│  └ middleware →    │ ◀───────────── │  synced_at     │ ◀────────────── │                    │
│    _outbox         │  pull (since)  │  deleted_at    │      push       │                    │
└────────────────────┘                └────────────────┘                 └────────────────────┘
```

### Локальная база (`lib/db/db.ts`)

- Новая IndexedDB `money-sync` с UUID-ключами (Dexie не умеет менять тип первичного ключа, поэтому новая база).
- **Очередь изменений `_outbox`** ведёт DBCore-middleware: любая запись/правка/удаление в синхронизируемой таблице в той же транзакции кладёт `{table, id, rev}` в очередь. Сервисы и экраны о синхронизации не знают.
- Middleware же выдаёт новым строкам UUID v7.
- Таблица `settings` — локальная (курсор, владелец данных), не синхронизируется.

### Детерминированные id (`lib/ids.ts`)

Два устройства, независимо создавшие «одно и то же», получают один id — upsert склеивает их:

| Что | id |
| --- | --- |
| Платёж по регулярному правилу на дату | `detId("recurring", recurringId, date)` |
| Автоотчисление от прихода в копилку | `detId("auto", incomeId, goalId)` |
| Продукт / магазин | `detId("product" \| "store", key)` |
| Стартовая категория | `detId("category", kind, name)` |

### Сервер (`supabase/migrations/*.sql`)

- PK `(user_id, id)` — одинаковые детерминированные id у разных пользователей не конфликтуют.
- `user_id default auth.uid()`; RLS: select/insert/update только своих строк; **DELETE запрещён** — только мягкое удаление `deleted_at`.
- `synced_at` ставит триггер (`clock_timestamp()`) — курсор pull, не зависит от часов устройств.
- Внешних ключей нет намеренно: пачки приходят в любом порядке.
- Все таблицы добавлены в публикацию `supabase_realtime`.
- Зарезервированные имена: `order → sort_order`, `limit → limit_amount`, `interval → every_n` (`lib/sync/mapping.ts`).

### Движок (`lib/sync/engine.ts`)

- **push**: читает очередь, для каждой таблицы (в порядке зависимостей) — `upsert` существующих строк (`on_conflict=user_id,id`, `deleted_at = null` — «воскрешение» после отмены удаления) и `PATCH deleted_at` для пропавших. Запись очереди снимается, только если её `rev` не сменился за время отправки.
- **pull**: строки с `synced_at > курсор − 2 мин` (перекрытие на случай коммитов не по порядку), постранично по 1000. Применяются в одной транзакции; строки с неотправленными локальными правками пропускаются. Записи очереди, созданные middleware при применении, удаляются — эха нет.
- **Конфликты**: last-write-wins по строке.

### Когда синхронизируется (`lib/sync/controller.ts`)

1. После входа: **pull → стартовые категории, если аккаунт пустой → регулярные платежи → push**. Сначала pull — иначе устройство затёрло бы данные аккаунта своими стартовыми.
2. Через ~1 с после любой локальной записи (пачкой).
3. По событию Realtime (изменение с другого устройства).
4. При возврате сети и на вкладку, раз в минуту.

Если в браузере остались данные другого аккаунта — они стираются перед первой синхронизацией. При выходе локальные данные стираются (в аккаунте остаются).

### Интерфейс

- Экран входа (вход / новый аккаунт), заставка первой синхронизации.
- Индикатор: «Всё синхронизировано», «Синхронизация…», «Нет сети — N изменений ждут отправки», «Ошибка» (клик — синхронизировать сейчас).
- Настройки → «Аккаунт и синхронизация»: почта, статус, «Синхронизировать», «Выйти».
- Демо-данные в режиме синхронизации скрыты (иначе пример попал бы в настоящий аккаунт).

## Перенос старых данных (`lib/db/legacy.ts`)

При первом запуске новой версии данные из старой базы `money` (числовые id, могли быть счета) переносятся в `money-sync`: счета → «Начальный остаток», переводы удаляются, id → UUID (категории, продукты, магазины — детерминированные), все ссылки переписываются. Перенесённое встаёт в очередь и уедет в аккаунт после входа. Тот же конвертер принимает резервные копии формата v1.
