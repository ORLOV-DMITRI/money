# Синхронизация через Supabase — дизайн

> Статус: **согласовано 2026-11-03**, к реализации.

## Сценарий

Один общий аккаунт на семью. Чаще всего — с компьютера, иногда — с планшета. Нужно, чтобы данные были одни и те же на всех устройствах и не терялись при очистке браузера.

Ответы на вопросы:

| Вопрос | Решение |
| --- | --- |
| Личные счета/копилки | Нет — всё общее |
| Отчёт «кто потратил» | Не нужен |
| Вход | Email + пароль, один аккаунт на двоих, сессия запоминается |
| Перенос данных | Не нужен, стартуем с чистого аккаунта |
| Бюджеты | Общие |
| Счета | Нет — «единые деньги» (см. DECISIONS) |

Поэтому **никаких «семей», приглашений и ролей**: каждая строка принадлежит пользователю (`user_id = auth.uid()`), и это единственное правило доступа.

## Принцип: local-first

```
 Компьютер                           Supabase                          Планшет
┌──────────────┐   push (outbox)   ┌──────────────┐    realtime     ┌──────────────┐
│ UI → Dexie   │ ────────────────▶ │  Postgres    │ ──────────────▶ │ Dexie → UI   │
│ (мгновенно)  │ ◀──────────────── │  + RLS       │ ◀────────────── │              │
└──────────────┘   pull (since)    └──────────────┘      push       └──────────────┘
```

Почему не «просто ходить в базу» без локальной копии:
- интерфейс, аналитика и подсказки уже построены на реактивной Dexie — меняется только слой записи, экраны не трогаем;
- ввод остаётся мгновенным, приложение не ломается при плохом интернете;
- аналитике всё равно нужна вся история на клиенте.

## Идентификаторы

Автоинкрементные id двух устройств столкнутся → **UUID v7**, генерируются на клиенте.

Детерминированные id там, где два устройства могут независимо создать «одно и то же»:

| Ситуация | Риск | Решение |
| --- | --- | --- |
| Регулярная «Аренда» в режиме «авто»: 7-го открыли и компьютер, и планшет | **аренда запишется дважды** | `id = uuidv5(recurring_id + ":" + date)` — вторая запись станет тем же upsert |
| Продукт «Молоко» добавлен с двух устройств | дубль продукта | `id = uuidv5(user_id + ":product:" + key)` |
| Магазин «Magnum» | дубль | `id = uuidv5(user_id + ":store:" + key)` |
| Стартовые категории | дубли при первом входе с двух устройств | детерминированные id от `user_id + имя по умолчанию` |

## Служебные поля

| Поле | Где ставится | Зачем |
| --- | --- | --- |
| `user_id` | Postgres (`default auth.uid()`), RLS | чьи данные |
| `updated_at` | **сервер**, триггер `now()` | курсор pull — не зависит от часов устройства |
| `deleted_at` | клиент | мягкое удаление, иначе удаление не дойдёт до второго устройства |
| `_dirty` | только Dexie | строка ждёт отправки |

## Синхронизация

- **Push**: пачками `upsert` всех `_dirty` строк в порядке зависимостей (категории → продукты/магазины → копилки → операции → позиции чека → бюджеты/регулярные/шаблоны). После успеха снимаем `_dirty`.
- **Pull**: по каждой таблице `updated_at > last_pulled_at` → `bulkPut` в Dexie, кроме строк, которые локально `_dirty` (они уедут следующим push).
- **Когда**: при входе, при возврате на вкладку, по событию Realtime, после каждой локальной записи (с задержкой ~1 с), раз в минуту как подстраховка.
- **Конфликты**: last-write-wins по строке. Вдвоём одну операцию одновременно правят редко.
- **Чек** (операция + позиции) отправляется одной RPC `upsert_receipt`, чтобы второе устройство не увидело операцию без позиций.
- **Статус** в интерфейсе: «Синхронизировано», «Синхронизация…», «Нет сети — 3 изменения ждут отправки».

## Вход

Email + пароль через Supabase Auth, сессия хранится в браузере. Экран входа появляется только если не залогинен. Регистрацию можно закрыть в настройках проекта после создания аккаунта.

## Что меняется в коде

- `lib/db`: Dexie v2 — UUID-ключи, служебные поля. Старых данных нет, поэтому миграция = новая база.
- `lib/services`: все записи через один слой, который ставит `_dirty`, делает мягкое удаление.
- `lib/sync`: push / pull / realtime / статус.
- `supabase/migrations/*.sql`: таблицы, RLS, триггеры `updated_at`, RPC `upsert_receipt`.
- UI: экран входа, индикатор синхронизации, «Выйти» в настройках.
- Тесты: два «устройства» (два экземпляра Dexie) против фейкового сервера; SQL-схема и RLS — на локальном Postgres.

## Инфраструктура

- Проект Supabase создаёт Дима; нужны `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` (публичный ключ, безопасность обеспечивает RLS).
- Миграции применяются через SQL Editor или `supabase db push`.
- Фронтенд остаётся статическим.
- Из среды разработки Claude Supabase недоступен — проверку на живом проекте делает Дима.
