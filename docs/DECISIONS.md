# Журнал решений

Формат: дата · решение · почему · последствия.

---

### 2026-11-03 · Без MVP: делаем полный набор функций сразу

**Почему.** Цель — показать возможности целиком, а не урезанную версию.
**Последствия.** План в `PLAN.md` разбит по модулям, а не по релизам. Модель данных сразу рассчитана на все фичи (чеки, копилки, регулярные), чтобы не было миграций в процессе.

### 2026-11-03 · Локальное хранение в IndexedDB (Dexie), без бэкенда

**Почему.** Ноль инфраструктуры, мгновенный отклик, работа офлайн, приватность (данные не уходят с устройства).
**Последствия.** Нет синхронизации между устройствами — компенсируем экспортом/импортом JSON. Доступ к данным изолирован в `lib/db` и `lib/services`, чтобы позже можно было заменить хранилище на API (например, Prisma + Postgres) без переписывания UI.

### 2026-11-03 · Суммы в тиынах (integer)

**Почему.** Float даёт ошибки округления (`0.1 + 0.2`). Тиыны редко используются, но целое число в минимальных единицах — стандартная практика для денег.
**Последствия.** Конвертация только на границе UI через `lib/money.ts`.

### 2026-11-03 · Даты операций строкой `YYYY-MM-DD`

**Почему.** Операция относится к календарному дню, а не к моменту времени; строка не «уезжает» при смене часового пояса и корректно сортируется лексикографически, что удобно для индексов Dexie.

### 2026-11-03 · Next.js 16 вместо 15

**Почему.** На момент старта актуальная стабильная версия — 16.x; начинать новый проект на предыдущей мажорной версии нет смысла.

### 2026-11-03 · Свои UI-компоненты в стиле shadcn/ui

**Почему.** Реестр shadcn недоступен из окружения разработки, а сам подход shadcn — это и есть «код компонентов в проекте». Пишем компоненты сами поверх Radix UI с теми же соглашениями (CSS-переменные, `cn()`, варианты через `class-variance-authority`).

### 2026-11-03 · Статический экспорт и детальные страницы через query-параметр

**Почему.** `output: 'export'` не умеет динамические маршруты без заранее известных id, а id живут только в IndexedDB пользователя. Поэтому детали — `/goals/view?id=3`, `/products/view?id=5`.

### 2026-11-03 · Отключили `cacheComponents` и `partialPrefetching` из шаблона Next 16.4

**Почему.** Это серверное кеширование и частичный пререндер, а у нас полностью клиентское SPA со статическим экспортом: данные приходят из IndexedDB, сервера нет.
**Последствия.** Конфиг проще; страницы, читающие `useSearchParams`, обёрнуты в `Suspense` (требование статического пререндера).

### 2026-11-03 · Структура расходов — ранжированные полосы, а не пончик

**Почему.** Категорий до 20, значения часто близки; пончик плохо сравнивает близкие доли и требует ≤ 6 сегментов. Полосы с подписью и суммой читаются сразу, цвет закреплён за категорией (сущностью), хвост сворачивается в «Остальное».

### 2026-11-03 · Цвета графиков «приход / расход» — зелёный и индиго, проверены валидатором

**Почему.** Классическая пара зелёный/красный почти неразличима при дейтеранопии (ΔE 6.9, в тёмной теме проваливает проверку яркости). Пара `#0f9f6e / #6366f1` (светлая) и `#1f9a6c / #7a6ef0` (тёмная) проходит все проверки, ΔE ≈ 22. Красный остаётся только как статус «плохо» (превышение бюджета) — вместе с текстом.

### 2026-11-03 · Сравнение незаконченного периода — с тем же числом дней прошлого

**Почему.** 3 ноября против всего октября даёт бессмысленное «−92%». В отчётах и на главной текущий период сравнивается с первыми N днями предыдущего; подсказки используют скользящие 30 дней.

### 2026-11-03 · Темп копилки — по трём полным календарным месяцам

**Почему.** Скользящее окно в 90 дней «теряло» ежемесячный взнос, если он попадал на день раньше границы: при взносах 65 000 ₸/мес темп показывался как ~47 000 ₸/мес.

### 2026-11-03 · Средние цены и требуемые взносы округляются до целых тенге

**Почему.** «597,66 ₸» и «167 048,79 ₸/мес» — шум. Расчёты идут в тиынах, округление только в итоговых показателях.

### 2026-11-03 · Свой service worker вместо PWA-плагина

**Почему.** Поведение простое (кеш статики + network-first для страниц), а плагины для Next часто отстают от мажорных версий. 60 строк, которые легко прочитать.

### 2026-11-03 · Supabase, один общий аккаунт, local-first

**Контекст.** Пользуются вдвоём как один человек: в основном с компьютера, иногда с планшета.
**Решение.** Supabase (Postgres + Auth). Один аккаунт по email и паролю, без семей и ролей; доступ — RLS `user_id = auth.uid()`. Локальная Dexie остаётся источником для UI, изменения синхронизируются в фоне.
**Почему не онлайн-only.** Экраны и аналитика уже реактивно работают от Dexie; меняется только слой записи. Плюс мгновенный ввод и устойчивость к плохой сети.
**Последствия.** UUID вместо автоинкремента; детерминированные id для регулярных платежей, продуктов и магазинов (иначе дубли с двух устройств); мягкое удаление; серверный `updated_at` как курсор.

### 2026-11-03 · «Единые деньги»: без счетов и переводов

**Контекст.** Разделение на Kaspi и наличные не нужно — для семьи это одни деньги.
**Решение.** Убрали счета и переводы из модели и интерфейса. Баланс — одна формула. Стартовый остаток и сверка с реальностью — операция-корректировка `adjustment` (может быть отрицательной, в отчёты не попадает). Депозит ведётся копилкой.
**Почему сейчас.** Перед переходом на Supabase: схема для синхронизации становится меньше (минус таблица и поле в каждой операции).
**Последствия.** Миграция Dexie v1 → v3 без потери денег: начальные остатки счетов превращаются в «Начальный остаток», переводы удаляются (они не меняли общий баланс). Нельзя сверяться с каждым кошельком отдельно — только с общей суммой, для этого есть «Сверить баланс».

### 2026-11-03 · Подсказка про дни недели — только при истории от 4 недель

**Почему.** По паре дней «самый дорогой день — вторник» — шум, а не закономерность.

### 2026-11-03 · Очередь изменений через Dexie-middleware, а не флаг `_dirty` в строках

**Почему.** Флаг пришлось бы ставить в каждом месте записи, а удаление вообще нечем пометить. Middleware на уровне DBCore видит все add/put/delete/clear и в той же транзакции пишет `{table, id, rev}` в `_outbox`. Сервисы не меняются, удаления не теряются.

### 2026-11-03 · PK `(user_id, id)`, без внешних ключей, DELETE запрещён

**Почему.** Детерминированные id одинаковы у разных пользователей — составной ключ исключает конфликты. Внешние ключи мешают отправке пачками в произвольном порядке. Физическое удаление сделало бы удаление «невидимым» для других устройств.

### 2026-11-03 · Без RPC `upsert_receipt`

**Почему.** Операция и позиции чека отправляются в одном цикле push по порядку таблиц; второе устройство может на долю секунды увидеть операцию без позиций, следующий pull это исправляет. Отдельная RPC не стоит усложнения.

### 2026-11-03 · Первая синхронизация: сначала pull, потом стартовые категории

**Почему.** Если устройство сначала создаст стартовые категории и отправит их, оно затрёт переименованные категории аккаунта. Поэтому: pull → категории, только если аккаунт пустой → push. Демо-данные в режиме синхронизации скрыты.

### 2026-11-03 · Курсор pull с перекрытием 2 минуты

**Почему.** `synced_at` ставится в момент записи строки, а транзакции коммитятся не строго по порядку — без перекрытия строку можно пропустить. Повторное применение тех же строк безвредно.

### 2026-11-03 · Подписи полей связаны с полями (`Field` выдаёт id)

**Контекст.** Сквозной тест экрана входа не нашёл поле по подписи «Почта».
**Решение.** `Field` генерирует id и связывает `<label htmlFor>` с полем и подсказкой (`aria-describedby`) — по всему приложению.
